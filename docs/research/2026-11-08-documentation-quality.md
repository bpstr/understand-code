# Documentation and specification quality review

Research date: **2026-11-08**. Audited revision: [`b5ae2e71d0751e2e030f97552c330f2236619ec2`](https://github.com/bpstr/understand-code/tree/b5ae2e71d0751e2e030f97552c330f2236619ec2).

## Finding

Understand Code already provides a strong foundation for trustworthy reconstruction: bounded investigations, exact source evidence, explicit uncertainty, review provenance, conservative freshness checks and protected maintainer notes. The main gap is the step from that semantic model to useful documentation for a particular reader. Its original concept pages and free-form `details` do not define document purpose, requirement authority, complete interface contracts or verifiable examples.

The changes tracked here add optional authored documents to the existing findings workflow. They preserve the source-reading boundary and the distinction between deterministic checks and accountable human/native review. The profile choices, authority model and readiness rules are project design decisions informed by the sources below; no source prescribes this exact JSON contract.

## Primary guidance reviewed

The following are concise paraphrases of original guidance and specifications. The last column states this project's application of that guidance.

| Source | Relevant guidance | Application and limit |
| --- | --- | --- |
| [Diátaxis](https://www.diataxis.fr/start-here/) and [Google: audience](https://developers.google.com/tech-writing/one/audience) | Different reader needs call for tutorials, how-to guides, reference and explanation; vocabulary and detail depend on readers' prior knowledge and goals. | Select a profile, audience, purpose and scope before drafting. Do not require every profile for every entity. The specification profile is our additional engineering use case. |
| [PEP 257](https://peps.python.org/pep-0257/) and [Go doc comments](https://go.dev/doc/comment) | Public-interface documentation adds behavior, parameters/results, side effects, errors, restrictions and relevant special cases beyond signatures. Caller contracts differ from internal implementation commentary. | Inspect relevant contract dimensions and language conventions. Recommend source comments without granting this tool authority to edit target code. Do not impose Python/Go syntax on other languages. |
| [Google: sample code](https://developers.google.com/tech-writing/two/sample-code) and [Rustdoc: documentation tests](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html) | Examples need usable setup, correct behavior and maintenance. Executable documentation can test examples; compiling and running are different checks. | Preserve literal examples, prerequisites and expected results. Record actual validation level and provenance; never turn source inspection into an execution claim or require a new language toolchain. |
| [Write the Docs: principles](https://www.writethedocs.org/guide/writing/docs-principles/) and [docs as code](https://www.writethedocs.org/guide/docs-as-code/) | Keep documentation current, discoverable and near code; avoid independently maintained overlapping sources. Version control, review and automated checks belong in the workflow. | Link canonical sources and managed entry points, record review triggers, and preserve update/review protections. Some explanatory repetition is useful; zero duplication is not the goal. |
| [Google: accessible documentation](https://developers.google.com/style/accessibility) | Clear heading hierarchy, meaningful link labels, plain language, text equivalents and copyable code make documentation easier to use. | Preserve paragraphs, ordered procedures, tables and literal examples; review the rendered result. Mechanical layout checks do not establish reader comprehension. |
| [NASA: good requirements](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/) and [requirements management](https://www.nasa.gov/reference/6-2-requirements-management/) | Requirements should be individually referenceable, clear, verifiable and traceable to their source; assumptions and incomplete values need explicit treatment. Maintain consistency with design and verification material as requirements change. | Use stable requirement IDs, basis, rationale, source/test evidence and verification intent. Separate existing behavior, documented intent and proposals. Adopt useful writing practices without importing NASA's organizational process. |
| [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119.html) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174.html) | BCP 14 defines requirement keywords; the special meanings apply to uppercase usage. Using these words is optional, and SHOULD permits justified exceptions. | Preserve the repository's convention and record it when relevant. Do not automatically adopt RFC terminology or confuse its SHOULD with another writing convention. |
| [arc42: runtime view](https://docs.arc42.org/section-6/) and [quality requirements](https://docs.arc42.org/section-10/) | Representative scenarios should cover important interactions and failures; quality scenarios need specific, measurable responses in their context. | Include relevant failure, security, quality and operational topics in a spec. Record unknown targets rather than inventing budgets; avoid documenting every possible runtime path. |
| [Michael Nygard: architecture decision records](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions) | Short decision records retain context, decision, status and consequences; superseded decisions remain useful history. | Link existing ADRs and keep proposed analysis separate from historical rationale. Do not manufacture a decision's motivation from current code. |
| [OpenAPI 3.2.1](https://spec.openapis.org/oas/v3.2.1.html) and [JSON Schema annotations](https://json-schema.org/understanding-json-schema/reference/annotations) | HTTP contracts describe parameters, payloads, responses and security, including operation-level overrides. JSON Schema defaults and examples are annotations, not proof of inserted values or validated examples. | Inspect the existing machine contract and implementation together; preserve the repository's dialect and expose mismatches. Reviewing a current OpenAPI version does not require migrating a target repository to it. |

## Acceptance and remaining judgment

The implementation contract is in the [authoring guide](../../skills/understand-code/references/documentation-authoring.md), [document schema](../../schemas/documentation.schema.json) and [workflow](../WORKFLOW.md#reader-facing-documents-and-specifications). Prepared examples live in [tests/fixtures/documentation](../../tests/fixtures/documentation/README.md); their provenance is synthetic test input, not a claim that the examples were executed.

Review a completed document for the following outcomes:

- The declared reader can find the relevant contract or follow the task with its stated prerequisites.
- Important defaults, boundaries, errors, side effects and unknowns match the inspected source; canonical docs or tests that disagree are identified.
- Each requirement has a clear basis, stable identity, rationale and a verification method with an observable expected result.
- Current behavior and proposed changes remain visibly separate; unsupported historical intent, approvals and quality targets are absent.
- Examples retain exact code and disclose the actual check level, snapshot and validation limits.
- Navigation, readable structure, maintenance triggers and protected maintainer notes survive regeneration.

The new gate makes missing structure, unsupported references and stale or absent attestations visible. It cannot decide whether arbitrary natural-language claims follow from evidence, whether a proposed requirement is the right product decision, or whether every relevant interface has been discovered. Source review and reader-focused review remain necessary.

No provider qualification or live-model evaluation is claimed. Automated checks use prepared fixtures under the [offline testing policy](../TESTING.md). Documentation authoring remains optional for ordinary reconstruction, and the skill recommends inline comment/docstring improvements without modifying target source implicitly.
